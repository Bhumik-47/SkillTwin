## Shared Schema & Architecture Contract

SkillTwin relies on a strict single source of truth across sub-systems:

> 📌 **Important**: Consult [`shared/schema.md`](shared/schema.md) before modifying any cross-component APIs, data models, or graph structures.

The contracts defined in `shared/schema.md` govern interactions between:
- **Frontend** (`frontend/`)
- **Backend API & DB Models** (`backend/`)
- **ML / BKT Engine** (`ml/`)
- **DAG Path Planner** (`backend/planner/`)
- **Gemini Agents** (`backend/agents/`)

Do not introduce new fields, change data types, or modify entity IDs without reviewing and updating `shared/schema.md`.

## AI-Assisted Development with Antigravity

SkillTwin is collaboratively developed using **Antigravity** and advanced agentic AI workflows. Contributors are welcome to use Antigravity, LLM-based pairing, or other AI coding assistants. However, human contributors remain strictly accountable for all committed code.

When using AI assistance, you must:
- **Review Generated Code**: Thoroughly read and inspect every file modified or generated by AI tools.
- **Verify Architecture Compatibility**: Ensure generated code adheres to existing design patterns, dependency boundaries, and type definitions.
- **Understand Key Changes**: Be prepared to explain the rationale, algorithmic complexity, and behavior of all submitted logic during PR review.
- **Enforce Security**: Verify that AI assistants do not introduce vulnerable dependencies, unsafe deserialization, injection risks, or weak crypto practices.
- **Prevent Secret Leakage**: Ensure AI tools never write API keys, tokens, or credentials into source files.
- **Run Verification Tests**: Never commit AI-generated code without running local test suites.

## GitHub Workflow & Branching Strategy

We follow a structured collaborative workflow to ensure stability on `main`:

```text
       main (Stable)
         │
         ▼
feature/<feature-name> (or fix/<fix-name>)
         │
         ▼
    development (Local iteration & testing)
         │
         ▼
    Pull Request (Against main)
         │
         ▼
    Peer Review & Automated Checks
         │
         ▼
    Merge into main
```

- `main`: Protected production-ready branch. All code in `main` must pass tests and build cleanly.
- `feature/<name>`: Dedicated branch for new features (e.g., `feature/custom-quiz-generator`).
- `fix/<name>`: Dedicated branch for bug fixes (e.g., `fix/bkt-posterior-overflow`).
- `docs/<name>`: Dedicated branch for documentation updates.

## Getting Started (Cloning & Setup)

### 1. Clone the Repository

```bash
git clone https://github.com/Bhumik-47/SkillTwin.git
cd SkillTwin
```

### 2. Configure Environment

Copy the example environment file:

```bash
cp .env.example .env
```

Ensure your `.env` file has the necessary variables configured (e.g., `GEMINI_API_KEY`, `SECRET_KEY`, `DATABASE_URL`). See [README.md](README.md#getting-started--setup-guide) for details.

### 3. Install Dependencies

**Backend:**
```bash
python -m venv venv

# Windows (PowerShell):
.\venv\Scripts\Activate.ps1
# Linux/macOS:
source venv/bin/activate

pip install -r backend/requirements.txt
```

**Frontend:**
```bash
cd frontend
npm install
cd ..
```

## Development Workflow

### Creating a Feature Branch

Always create a new branch off the latest `main`:

```bash
git checkout main
git pull origin main
git checkout -b feature/your-feature-name
```

### Syncing with Main

Keep your feature branch updated regularly to minimize merge conflicts:

```bash
git fetch origin
git rebase origin/main
# or: git merge origin/main
```

### Making Commits & Commit Message Guidelines

We recommend the [Conventional Commits](https://www.conventionalcommits.org/) specification:

```text
<type>(<scope>): <short description>

[optional body]

[optional footer]
```

#### Common Types:
- `feat`: A new feature or capability
- `fix`: A bug fix
- `docs`: Documentation only changes
- `test`: Adding or correcting tests
- `refactor`: Code change that neither fixes a bug nor adds a feature
- `perf`: Code change that improves performance
- `chore`: Maintenance tasks, dependency updates, configuration

#### Examples:
- `feat(planner): add local subgraph repair for prerequisite gaps`
- `fix(bkt): resolve slip parameter boundary condition in scoring`
- `docs(readme): update setup guide with docker compose instructions`
- `test(frontend): add acyclicity assertion for backend engineering DAG`

## Testing & Verification Requirements

Before committing and opening a Pull Request, you **must run all test suites** and verify that the build succeeds:

### 1. Backend Tests (Pytest)
```bash
pytest
```

### 2. Frontend Mathematical & DAG Tests
```bash
cd frontend
node --test src/tests/engine.test.mjs
```

### 3. Frontend Production Build Check
```bash
npm run build
cd ..
```

Ensure all tests pass with zero errors.

## Submitting a Pull Request

1. **Push your branch** to GitHub:
   ```bash
   git push -u origin feature/your-feature-name
   ```
2. **Open a Pull Request** targeting the `main` branch.
3. Fill out the [Pull Request Template](.github/pull_request_template.md) completely:
   - Provide a clear summary of what changed and why.
   - Attach screenshots or recordings for UI updates.
   - Check all items in the submission checklist.
4. Address any review comments or feedback promptly.

## Security & Secrets Policy

We take security seriously. Please uphold these non-negotiable rules:

- ❌ **NEVER commit sensitive credentials**, including:
  - Google Gemini API Keys (`GEMINI_API_KEY`)
  - JWT Secret Keys (`SECRET_KEY`, `JWT_SECRET_KEY`)
  - Database passwords or connection URIs containing credentials
  - Production or personal `.env` files
- Always keep secrets in `.env` (which is git-ignored by default).
- If you accidentally commit a secret, notify maintainers immediately and rotate the compromised credential.
- For reporting security vulnerabilities, follow the steps in [SECURITY.md](SECURITY.md).
